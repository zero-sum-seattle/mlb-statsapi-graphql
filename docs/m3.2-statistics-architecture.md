# M3.2: curated player season statistics architecture

Status: proposed design for [issue #10](https://github.com/zero-sum-seattle/mlb-statsapi-graphql/issues/10).
M3.2 is a research milestone; acceptance happens through review of this PR.
The SDL below is a proposal, not the running public schema. No production types,
resolvers, loaders, dependencies, or M3.1 behavior change in this milestone.
The [M3.3 implementation plan](m3.3-player-season-statistics-plan.md) is a follow-up,
not an implementation commitment.

## Decision

Add only `Player.seasonHitting(season:)` and `Player.seasonPitching(season:)` in
the next milestone, fixed to regular-season MLB statistics. Each returns a
small typed envelope containing **splits with provenance**, rather than a
single purported season total. Use curated Strawberry data transfer objects
(DTOs), not Pydantic-generated GraphQL types or a JSON scalar.

Do not choose the first split, sum all splits, or silently promote a single
team row to a complete season. A returned multi-team row can overlap its team
rows. Its scope metadata is useful, but does not establish endpoint completeness.
There is deliberately no `total`, `isComplete`, or aggregate-selection algorithm
in this first contract. This trades a little client work for honest semantics
and leaves room for a separately researched authoritative-total field later.

## Upstream methods and return shape

The locked [`async_mlb.py`](https://github.com/zero-sum-seattle/python-mlb-statsapi/blob/74f337ab8a45c43777ec8087c14c5f6719ff5cea/mlbstatsapi/async_mlb.py#L2029)
implements:

| Method | v1 endpoint | Request shaping |
| --- | --- | --- |
| `get_player_stats(person_id, stats, groups, **params)` | `people/{id}/stats` | Adds `stats` and singular query key `group` from the lists; forwards other keyword arguments |
| `get_team_stats(team_id, stats, groups, **params)` | `teams/{id}/stats` | Same shaping; used by existing M3.1 |
| `get_stats(stats, groups, **params)` | `stats` | Same shaping; population filters, ranking, limits, and completeness depend on this endpoint, not the return annotation |
| `get_players_stats_for_game(person_id, game_id, **params)` | `people/{id}/stats/game/{game_id}` | Forwards keyword arguments; does not add season stats/group lists on its own |

All four use the same [`parse_split_stats`](https://github.com/zero-sum-seattle/python-mlb-statsapi/blob/74f337ab8a45c43777ec8087c14c5f6719ff5cea/mlbstatsapi/_parsers/stats.py)
and [`create_split_data` / `return_splits`](https://github.com/zero-sum-seattle/python-mlb-statsapi/blob/74f337ab8a45c43777ec8087c14c5f6719ff5cea/mlbstatsapi/mlb_module.py#L42):

```text
HTTP JSON: {stats: [{group: {displayName}, type: {displayName}, splits: [...]}]}
  -> dict[group][type]
  -> Stat(group, type, total_splits, splits)
  -> HittingSeason(Split).stat: SimpleHittingSplit
     or PitchingSeason(Split).stat: SimplePitchingSplit
```

`MLBBaseModel` is Pydantic v2 with camel-case aliases, population by Python
field name, unknown fields ignored, and number-to-string coercion enabled.
`Split` holds optional `season`, `team`, `player`, `sport`, `league`, `game_type`,
`num_teams`, `num_leagues`, `position`, and `rank`; empty identity dictionaries
become `None`. `Stat.splits` is an optional **unparameterized list**, not a
static union guaranteeing the correct row type. The explicit mapper must check
the expected block and concrete row/payload model before reading attributes.

## Upstream inventory and parser limits

The [captured statGroups](research/m3.2/fixtures/stat-groups.json) advertise
`hitting`, `pitching`, `fielding`, `catching`, `running`, `game`, `team`, and
`streak`. The [captured statTypes](research/m3.2/fixtures/stat-types.json) contain
61 names. These global catalogs do **not** guarantee every group/type/endpoint
combination is meaningful, populated, or parseable.

The full [registration table](research/m3.2/parser-inventory.md) records exact
type strings, concrete row models, and payload models. In particular:

| Group | Relevant registrations and limitations |
| --- | --- |
| hitting | `season -> HittingSeason -> SimpleHittingSplit`; also career, year-by-year, date/month/home-away/win-loss splits, matchups, game/play/pitch logs, advanced, expected statistics, and sabermetrics |
| pitching | `season` and `statsSingleSeason -> PitchingSeason -> SimplePitchingSplit`; other basic/advanced/log/matchup registrations exist. The `vsTeam*` rows unexpectedly use `SimpleHittingSplit`; do not generalize season payload types to all pitching types |
| fielding | Basic, advanced-named, career, logs, and situational registrations all use `SimpleFieldingSplit`; naming alone does not establish advanced coverage |
| catching | Basic and situational types use `SimpleCatchingSplit`; `CatchingGameLog` declares metadata but no `stat` payload field |
| running | Only `opponentsFaced`; `RunningOpponentsFaced` inherits `Stat` rather than `Split` and has no `stat` field. Registration is not evidence it parses arbitrary live rows |
| game | Models use `_type`, while dispatch searches `_stat`; a nonempty season response parses to an empty split list in the probe |
| team / streak | No `_stat` registrations; empty module / placeholder respectively |
| fallback `stats` | Used when a group is absent: registrations for `gameLog` (dictionary payload), pitch arsenal, zones, spray charts, and outs above average; not an advertised stat group |

Important verified information loss and failure modes:

1. Missing/empty body or `stats` returns `{}`. Empty raw split arrays omit the
   group/type block. Rows with absent, null, or empty `stat` are skipped.
2. `total_splits` uses raw `totalSplits` if present, otherwise raw split count.
   It can exceed the parsed row count; it is not a completeness or pagination
   guarantee. None of the six captured player responses includes `totalSplits`.
3. Dispatch dynamically imports the response group module and scans `_stat`
   registrations. Unknown groups can raise `ModuleNotFoundError`; an unknown
   type in a known group can yield an empty `Stat.splits` with a positive count.
4. Repeated response blocks with the same group/type overwrite earlier blocks.
   Unknown metadata is discarded by Pydantic. A nonempty `stat` containing only
   unknown keys can parse to an all-null basic payload. Parsed data cannot fully
   reconstruct the raw response or prove no rows were lost.
5. Missing response type defaults to `gameLog`; missing response group defaults
   to `stats`. That fallback can carry an arbitrary dictionary. It is explicitly
   outside the curated season mapper.

Do not repair or bypass these dependency behaviors in M3.2/M3.3. They explain
why a universal schema or claim of exhaustive splits would be premature.

## Representative split semantics

All player captures use explicit `stats=season`, `season`, `gameType=R`,
`sportIds=1`, and both hitting and pitching groups. The locked client encodes
the groups as repeated `group=hitting&group=pitching` query parameters. Each
capture passed the locked parser in the live call and the offline replay.
No block is fabricated when a requested group is absent.

| Capture | Observed rows and metadata | Design implication |
| --- | --- | --- |
| [Soto 2024](research/m3.2/fixtures/soto-2024.json) | One hitting row, team 147, player 665742, season `2024`, game type `R`, sport 1, league 103; `numTeams` absent | A single team-associated row is useful but not independent proof of a complete season |
| [Soto 2022](research/m3.2/fixtures/soto-2022.json) | Hitting: no-team row with `numTeams=2`, then teams 120 and 135; all league 104. Home runs 27, 21, 6 | All-row summation gives 54, double counting the observed aggregate. Array position is not a selection rule |
| [Soto 2022 with teamId=120](research/m3.2/fixtures/soto-2022-team.json) | Same three statistics rows as the unfiltered request | Forwarding a parameter does not prove endpoint filtering. Exclude a public team filter initially |
| [Scherzer 2023](research/m3.2/fixtures/scherzer-2023.json) | Pitching: no-team row `numTeams=2`, `numLeagues=2`, no league; then teams 121/140 with leagues 104/103. Innings `152.2`, `107.2`, `45.0` | Aggregate league may legitimately be absent; retain team/league scope and innings notation |
| [Ohtani 2023](research/m3.2/fixtures/ohtani-2023.json) | Both hitting and pitching blocks for player 660271 and team 108 | Group availability must be independent of primary position; no hitter/pitcher exclusivity |
| [Ohtani 2024](research/m3.2/fixtures/ohtani-2024.json) | Hitting only, team 119; requested pitching block absent | Missing pitching is unavailable data, not a zero pitching season or an error |

`numTeams > 1` plus no team is evidence that a row describes multiple teams;
it does not prove all teams, leagues, or games are represented. No-team alone
is insufficient to identify an aggregate. Team rows need not be disjoint stints
(a player might return to a team). Never infer stint identity from team ID alone,
deduplicate statistics rows by team ID, or average their rates.

## Proposed public SDL

This is an additive proposal for Strawberry's normal snake_case-to-camelCase
conversion. The `extend` assumes the existing `Player` type. It adds no generic
group/type inputs, JSON, interfaces, or recursive entity links.

```graphql
extend type Player {
  seasonHitting(season: Int!): PlayerSeasonHitting
  seasonPitching(season: Int!): PlayerSeasonPitching
}

type PlayerSeasonHitting {
  playerId: Int!
  season: Int!
  gameType: String!
  splits: [PlayerSeasonHittingSplit!]!
}

type PlayerSeasonPitching {
  playerId: Int!
  season: Int!
  gameType: String!
  splits: [PlayerSeasonPitchingSplit!]!
}

enum PlayerSeasonSplitScope {
  TEAM
  MULTI_TEAM
  UNSPECIFIED
}

type PlayerSeasonSplitProvenance {
  parsedIndex: Int!
  scope: PlayerSeasonSplitScope!
  playerId: Int
  season: String
  gameType: String
  teamId: Int
  leagueId: Int
  sportId: Int
  numTeams: Int
  numLeagues: Int
}

type PlayerSeasonHittingSplit {
  provenance: PlayerSeasonSplitProvenance!
  gamesPlayed: Int
  plateAppearances: Int
  atBats: Int
  runs: Int
  hits: Int
  doubles: Int
  triples: Int
  homeRuns: Int
  runsBattedIn: Int
  walks: Int
  strikeouts: Int
  stolenBases: Int
  battingAverage: Float
  onBasePercentage: Float
  sluggingPercentage: Float
  onBasePlusSlugging: Float
}

type PlayerSeasonPitchingSplit {
  provenance: PlayerSeasonSplitProvenance!
  gamesPlayed: Int
  gamesStarted: Int
  wins: Int
  losses: Int
  saves: Int
  inningsPitched: String
  outs: Int
  hitsAllowed: Int
  runsAllowed: Int
  earnedRuns: Int
  homeRunsAllowed: Int
  walks: Int
  strikeouts: Int
  earnedRunAverage: Float
  walksAndHitsPerInningPitched: Float
}
```

Identity fields use `Int`, matching existing team/player IDs; no ID scalar
migration is included. Envelope `playerId`, `season`, and `gameType="R"` identify
the **request**. Nullable provenance values report exactly what the parsed row
supplies; do not fill them from the request. `parsedIndex` is the zero-based
index in the library's parsed block before mapper filtering, not an MLB ID,
raw JSON offset, or stable cross-request identifier. Preserve order and duplicate
rows; indices can have gaps after filtering.

`scope=TEAM` means a team ID exists and `numTeams` is absent or 1;
`MULTI_TEAM` means no team ID and `numTeams > 1`; otherwise use `UNSPECIFIED`,
including conflicting team-plus-multiple-team metadata. These labels describe
association, never completeness. Do not invent a team ID for a multi-team row.
Team/player identifiers are scalar attributes, so reading provenance performs
no team/person lookups and does not enable recursive statistics fan-out.

## Mapping, missing values, and numeric policy

The future mapper consumes only the expected `Stat` block and concrete
`HittingSeason/SimpleHittingSplit` or `PitchingSeason/SimplePitchingSplit`.
It returns plain curated DTOs; keep Pydantic imports, model introspection, and
raw dictionaries behind that boundary. Separate the player mapper from M3.1's
whole-team total selector; do not build a general registry/framework.

| Input condition | Proposed GraphQL behavior |
| --- | --- |
| Invalid season outside 1000–9999 | Existing `BAD_USER_INPUT`, before statistics loading; four digits do not promise historical coverage |
| No block, no parsed splits, or no accepted rows | Nullable season field returns `null`, without an error |
| Supplied player/season/game type/sport differs from requested player/year/`R`/1 | Exclude that row; do not relabel it. Missing optional metadata is accepted and remains nullable in provenance |
| Position-specific season row | Exclude from this basic season interface; do not silently claim it is a whole-player row |
| Multiple matching or indistinguishable rows | Return each typed row with provenance; no chosen total, sum, merge, or value-based deduplication |
| Missing or explicit-null metric | Nullable leaf `null`; the public interface intentionally collapses these two states |
| Actual zero | Preserve `0` / `0.0` |
| Parsed row with only unavailable curated metrics | Retain it with all-null metrics and provenance, unlike M3.1's total projection; it still describes an observed row |
| Block/model mismatch, malformed mapped value, nonfinite rate | Fail this season field with client-safe `UPSTREAM_ERROR`; never silently turn corruption into zero or missing data |

If the expected dictionary key exists but `Stat.group/type` disagrees, treat it
as a block mismatch, not as absence. Filter incompatible scope metadata only
after checking row/payload types. An unsupported group that the parser cannot
import remains an unexpected upstream exception under existing error masking;
do not catch every exception as no data. `splits` and its elements are non-null
inside a successful envelope; empty successful lists are not used initially.
The parent season field is nullable so one group's failure need not erase the
other group's data.

Most leaf names are direct camel-case versions of upstream attributes. Explicit
exceptions define meaning rather than exposing abbreviations:

| GraphQL leaf | Upstream attribute | Meaning / unit |
| --- | --- | --- |
| `runsBattedIn` / `walks` | `rbi` / `base_on_balls` | Hitting RBI / walks; pitching walks are walks issued |
| `strikeouts` | `strikeouts` (wire `strikeOuts`) | Hitter strikeouts or pitcher strikeouts, according to containing type |
| `battingAverage`, `onBasePercentage`, `sluggingPercentage`, `onBasePlusSlugging` | `avg`, `obp`, `slg`, `ops` | Numeric upstream rate/ratio; `.287` becomes `0.287`, not `28.7` |
| `hitsAllowed`, `runsAllowed`, `homeRunsAllowed` | `hits`, `runs`, `home_runs` | Pitching values; runs include unearned runs |
| `earnedRunAverage` / `walksAndHitsPerInningPitched` | `era` / `whip` | Upstream ERA / WHIP, not a recomputation from rounded values |
| `inningsPitched` / `outs` | `innings_pitched` / `outs` | Innings notation string / integer count of outs |

Counts are nullable GraphQL signed 32-bit integers. Reject negative counts,
nonpositive IDs, and out-of-range mapped integers at the mapping boundary
rather than overflowing serialization; preserve missing IDs as null. Rates use GraphQL `Float` (binary
double precision) because the locked library has already converted decimal
strings to Python floats. Display zeros and trailing precision are not retained:
`"1.000"` becomes `1.0`. Clients format batting rates to three decimal places
and ERA/WHIP as desired. No exact decimal, percentage rescaling, or uniform
0–1 constraint is promised (OPS/slugging can exceed 1). Advanced percentages
whose units differ are excluded.

The library normalizes only `".---"` and `"-.--"` to `None` for applicable float
fields; other malformed strings such as `"N/A"` raise `ValidationError`.
Missing and explicit-null basic fields default to `None`. Probes also show
`"NaN"` can parse to a float, so the mapper must require finite rates before
GraphQL serialization. Do not add broad placeholder-string coercion.

Innings remain a string: `"6.2"` means six innings and two outs, or 20 outs,
not 6.2 decimal innings. Accept only canonical nonnegative `N.0`, `N.1`, `N.2`
for a supplied innings value; the library itself also accepts malformed
`"6.3"`. Preserve the notation, do not sum it as a float. If `outs` is also
supplied, require `outs = 3*N + suffix`; inconsistency is an upstream error.
If either is missing, keep that leaf null rather than deriving it. This check
is local consistency checking, not an aggregation algorithm. Scherzer's
`"152.2"` and 458 outs demonstrate the distinction.

## Loading, cost, and operational behavior

Use one request-scoped player-season loader shared by both fields, fetching both
small basic groups in one logical call. This avoids two calls for a two-way
player. Selecting hitting alone still fetches pitching in the same response;
this modest overfetch is explicit. A dependency parse failure in either block
can therefore fail both fields sharing this key. Mapping failures after a
successful load remain field-local. Separate per-group loaders would improve
parser failure isolation but double calls for common combined queries; defer
that tradeoff unless evidence shows it matters.

```python
# Proposed only; not production code.
key = (player_id, season, "season", ("hitting", "pitching"), "R", 1)
await lookups.run("player_season_stats", lambda: mlb.get_player_stats(
    player_id, stats=["season"], groups=["hitting", "pitching"],
    season=season, gameType="R", sportIds=1,
))
```

The key encodes **all response-shaping arguments**, including fixed policy
values. Do not include projection choice (hitting versus pitching), GraphQL
aliases, field selections, or player display names. No dynamic group/order,
team filter, league filter, date, hydration, limit, or game-type inputs are
accepted. If any becomes configurable later, change both cache and cost
identities together. A fixed, canonical group tuple avoids order-related misses.

Declare both fields next to their Strawberry resolvers with weight **5** and
the same `request_key`:

```python
priced(5, request_key=lambda parent, args:
    ("player_season_stats", parent, args["season"], "season",
     ("hitting", "pitching"), "R", 1) if parent is not None else None)
```

This is the namespace plus the exact loader key. `Query.player` already passes
the player ID as its `result_key`. No `result_key` is needed on the season
fields initially: their descendants are plain, preloaded DTO attributes. Any
custom computation resolver introduced for scope/formatting must declare
`priced(0)` and perform no upstream work. Prefer computing these values in the
mapping layer. Do not put Pydantic model instances into public DTO fields.

| Proposed operation | Estimated cost | Logical calls absent errors |
| --- | ---: | --- |
| One root player, basic identity only | 5 | One person lookup |
| One root player, hitting and pitching for the same season, even under aliases | 10 | One person + one combined statistics lookup |
| Same player, two seasons | 15 | One person + two statistics lookups |
| Two root players, each with both groups for one season | 20 | Two people + two statistics lookups |
| `team { roster { player { seasonHitting(...) { ... } } } }` | Infinite, rejected before execution | Zero |

The roster has no contractually finite bound; its elements have unknown IDs
during estimation. Adding a costed descendant is therefore rejected even if a
particular live roster happens to be short. Keep this behavior and document it
when implementing. Do not fabricate `max_items=26/40`, pre-charge only one
player, or change roster behavior in this milestone.

Statistics split lists also have **no verified finite bound**. They require no
descendant I/O, so existing traversal allows their free scalar/provenance
selection without `max_items`. Do not expose `team: Team` or `player: Player`
links that allow costed descendants. Do not truncate splits silently to invent
a bound. The cost budget limits logical requests, not upstream body size,
parser CPU, split count, or response bytes; unbounded response-size exposure
remains an explicit operational limitation. A hard limit would need a separate
documented failure policy, not a misleading estimator declaration.

Reuse `_fetch_each`, cached failed futures, request-local cancellation, and
the shared admission path. Distinct player/season keys remain distinct HTTP
lookups; there is no backend batch API in this design. Cache hits add no lookup
observations. The new lookup kind is `player_season_stats`; its timings include
library parsing/retries as with existing kinds. The per-worker semaphore does
not bound waiting work, cap response size, or impose an overall deadline.

## Upstream errors

The default client uses `strict_http=True`. The adapter raises `MlbHttpError`
for final non-404 4xx (including 400/429) and 5xx; a 404 returns an empty result,
and these four methods return `{}`. Do not read the method's broad 4xx guard
as proof that all 4xx are swallowed: strict adapter errors happen first.
This is verified with the installed client and injected HTTPX transport.

Known `TheMlbStatsApiException` subclasses (HTTP, transport, timeout, decode)
and Pydantic `ValidationError` retain the existing client-safe `UPSTREAM_ERROR`
path. Preserve failure caching per key and fresh caches next request; aliases
may each report their own GraphQL error path for one failed lookup. Other keys
can still succeed. Unexpected errors retain existing generic masking/server
logging. Do not expose response bodies, URLs with internal context, raw library
exception messages, or silently retry outside the existing library policy.

## Unresolved questions and explicit limits

- No exhaustive endpoint/group/type capability matrix was tested. Only the
  historical player-season cases above were fetched live; other methods were
  studied in source and replayed offline. Global metadata catalogs are discovery
  aids. Their contents can change independently of the locked parser.
- Captures do not establish an ordering, exhaustive season completeness,
  maximum split count, pagination contract, or a universal aggregate marker.
  Missing `numTeams`, league-only aggregates, returning-to-team stints, and
  duplicate indistinguishable rows need broader evidence before a total helper.
  Unknown/lost metadata and duplicate block overwrites are library limitations.
- `teamId=120` did not filter the captured player endpoint response. No team
  filter is proposed. The fixed sport/game-type parameters are request intent;
  validate echoed metadata when present rather than promising the server always
  honors every parameter. Broader historical/minor-league coverage is unverified.
- Missing game-type metadata is accepted from the explicitly regular-season
  request, while provenance remains null. This follows the existing optional
  metadata approach; it is not evidence that the row explicitly said `R`.
- Current fixtures include a same-league traded hitter, a cross-league traded
  pitcher, and two two-way-player seasons. They do not establish behavior for
  every trade/league/history edge case. Synthetic ambiguity probes are labeled
  separately and must not be presented as live observations.

Advanced stats (even when present in `Simple*` models), career/year-by-year
queries, game/play/pitch logs, date ranges, rankings/leaderboards, generic stats
passthrough, calculated totals, and new team-stat fields are excluded from the
first implementation. Resolving these questions is not required to ship honest
typed split rows. M3.2 closes only through acceptance of this design PR; M3.3
requires its own implementation, tests, and review.
